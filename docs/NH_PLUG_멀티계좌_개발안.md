# NH증권 PLUG — 멀티브로커·멀티계좌 확장 개발안 (설계만 · 미구현)

> 상태: **개발안 단계. 코드 미작성.** 사용자 요청(2026-08): "NH 계좌 2개 추가, 방법론만 먼저".
> 구현은 본 문서의 P0 게이트 통과 + 사용자 승인 후 진행.

## 1. 배경

- **NH투자증권 PLUG OpenAPI 출시 (2026-08-10)**: 나무 PLUG / N2 PLUG.
  - **REST API** — 운영 `api.nhplug.com:8443`, **모의투자 `moapi.nhplug.com:8443`** (스테이징에 유리)
  - 공식 **Python SDK** (`github.com/PLUG-OpenAPI/nhplug-sdk`, 샘플 포함) + MCP 서버
  - 국내·해외주식/파생/채권/금현물, 수수료 국내 0.01% · **해외 0.09%** (업계 최저)
- 과거 결론 갱신: 구 QV Open API(윈도우 32bit DLL·국내주문 전용·2026 TR 단종)는 부적합 판정했으나(VR 사양서 §6.5), **PLUG는 REST + 해외주식 지원이라 재검토 성립.** 단 세부 스펙 검증 필요(§3).
- 목표: 기존 **KIS 계좌 1개(69567573, 3전략)** 에 **NH 계좌 2개**를 추가해 멀티브로커·멀티계좌 플랫폼으로 확장.

## 2. 현 아키텍처의 전제 (바뀌어야 할 것)

| 현재 전제 | 멀티계좌에서의 변화 |
|---|---|
| 브로커 = KIS 하나 (전략 패키지마다 `kis_client.py` 내장) | **브로커 추상화 계층** 필요 (KIS/NH 공통 인터페이스) |
| 계좌 = 공용 1개 (전략별 자격을 각 DB system_config에 저장) | **계좌 레지스트리** (계좌 N개, 전략 인스턴스↔계좌 바인딩) |
| 티커 전역 무중복 (단일계좌 체결 귀속 안전장치) | **계좌 스코프 무중복으로 완화** — 계좌가 다르면 같은 티커 허용 |
| 스케줄 레인 = 단일 계좌 내 시간 분리 | 레이트리밋은 브로커·앱키 단위 → **KIS레인과 NH레인은 독립**, NH 계좌끼리만 분리 |
| 대시보드/집계 = 계좌 1개 암묵 가정 (holdings·equity·metrics) | **계좌 차원 추가** (통합 뷰 + 계좌별 필터) |

사용자 발급 앱키로 실측 완료 (읽기전용만, 주문 없음. 키는 `~/.nhplug/.env` 로컬 보관·레포 밖):

| 항목 | 결과 |
|---|---|
| **③ LOC/MOC** | ✅ **지원** — 정본 스펙(gbstock/openapi.json) 호가유형: `12.LOC(장마감 지정가)`, `14.MOC(장마감 시장가)` + LOO/MOO/STOP/STOP LIMIT/TWAP/VWAP. **매수 스키마에도 12·14 명시** → KIS의 'MOC 매수 불가' 제약 없어 보임(모의 실측은 P6) |
| ① 인증 | ✅ 실측 — POST /oauth2/token, **토큰 24h**·파일캐시(`~/.nhplug/`), 발급은 운영서버 전용(moapi 미제공). 재발급=보안알림 1건이라 캐시 필수 |
| ② 주문/조회 세트 | ✅ 스펙 존재 — buy/sell/modify/cancel + **reservedSubmit/reservedCancel(예약주문!)** + unexecuted/balance/dailyTransaction/periodPnl/margin |
| ④ 시세 | ✅ 실측 — /gbstock/quote/v1/current 로 TQQQ(프로셰어즈 QQQ 3배 ETF·나스닥) 조회 성공. period(기간시세)로 전일종가 가능 |
| ⑦ 모의투자 | 서버 존재(moapi.nhplug.com:8443) — 주문 실측은 P6에서 |
| ⑤ 레이트리밋 / ⑥ WebSocket(gbstock 실시간) | 미확인 — llms.txt·realtime 스펙 P1에서 확인 |
| 계좌 | ✅ 계좌목록 조회 성공 — 앱키에 **여러 계좌 연결됨**(끝자리 …977/…635/…343/…374 등). **어느 2개를 쓸지 사용자 지정 필요** |

공식 문서·SDK·모의서버로 아래를 확인한다. **③이 안 되면 전면 재설계**(§3.1).

| # | 검증 항목 | 왜 중요한가 |
|---|---|---|
| ① | REST 인증 방식 (앱키/토큰, 만료·갱신, 계좌 2개=앱키 2개?) | 클라이언트 설계·토큰 캐시 구조 |

| ③ | **미국주식 LOC/MOC 주문유형 지원 여부** | **전 전략의 생명선** — 무한매수법·떨사오팔·종사종팔 전부 LOC(+손절 MOC) 기반 |

### 3.1 ③ LOC/MOC 미지원 시 대안 (사용자 결정 필요)
- (a) NH 계좌는 **장마감 임박 지정가**로 근사 (예: 마감 5분 전 현재가±버퍼 지정가 제출) — 전략 변형이라 별도 검증·승인 필수
- (b) NH 계좌는 **LOC 불필요 전략 전용** (예: VR — 2주 리밸런싱은 일반 지정가로 충분)
- (c) NH 계좌 추가 보류

## 4. 목표 아키텍처

### 4.1 브로커 추상화 계층 — `core/brokers/`
```
core/brokers/
  base.py      # BrokerClient 인터페이스(추상):
               #   auth() / inquire_balance() / inquire_ccnl() / inquire_nccs()
               #   inquire_prev_close() / order() / order_cancel()
               #   ※ 반환 스키마를 공통 정규형으로 통일 (지금 워커가 쓰는 df 컬럼 기준)
  kis.py       # 기존 kis_client를 '감싸는' 어댑터 — 검증된 KIS 코드는 무수정
  nh_plug.py   # 신규 NHPlugClient (공식 nhplug-sdk 기반, LOC/MOC 매핑 포함)
```
- **원칙**: 운영중 KIS 메커니즘 무변경. 어댑터는 위임(wrapping)만.
- 워커가 `client.XXX()`를 호출하는 형태는 유지하고, 계좌의 브로커에 따라 주입되는 클라이언트만 달라짐.

### 4.2 계좌 레지스트리 — `core/account_registry.py`
```yaml
# core/_accounts.yaml (gitignore, 배포 보존)
accounts:
  kis_main:  {broker: kis, account_no: "69567573", alias: "KIS 본계좌"}
  nh_1:      {broker: nh_plug, account_no: "XXXXXXXX", alias: "NH 1호"}
  nh_2:      {broker: nh_plug, account_no: "YYYYYYYY", alias: "NH 2호"}
```
- 자격증명(앱키/시크릿)은 계좌별로 분리 저장(기존 system_config 방식 계승 or 파일). UI 시스템설정에서 입력 (보안상 마스킹).

### 4.3 전략 인스턴스 = (전략로직 × 계좌)
현 구조는 "패키지 = 전략 = 계좌" 고정. 확장 방향 두 가지:

| 방식 | 내용 | 장단점 |
|---|---|---|
| **A. 인스턴스 주입형 (권장)** | 전략 패키지를 `(instance_id, account_id, db_path)` 파라미터로 기동. 예: `jongsa@nh_1` → `jongsa_nh1.db` | 코드 중복 없음·확장 유연. 단 패키지 내부의 전역 상수(DB경로·킬스위치)를 인스턴스 컨텍스트로 바꾸는 리팩터 필요(코어 로직은 무변경, 배선만) |
| B. 패키지 복제형 | 종사종팔 때처럼 `strategies/jongsa_nh1/` 복제 | 검증된 최소변경 패턴. 인스턴스 수만큼 코드 중복·수정 전파 부담 |

→ NH 2계좌 + 향후 확장을 고려하면 **A 권장**. 단 1차 도입(계좌 2개·전략 2인스턴스 수준)은 B로 시작해도 무방 — P1에서 최종 결정.

### 4.4 티커 유일성 — 계좌 스코프로 완화
- 불변식 변경: ~~전 전략 전역 무중복~~ → **"같은 계좌 안에서 무중복"**
- 근거: 무중복의 목적은 단일계좌에서 체결·잔고·미체결을 티커→전략으로 귀속시키는 것. 계좌가 다르면 귀속이 계좌 단위로 자연 분리됨.
- 효과: **KIS의 TQQQ(무한매수법)와 NH1의 TQQQ(예: VR)가 공존 가능** — VR의 TQQQ 충돌 문제 해소 경로.
- `ticker_registry`: `find_owner(ticker, account_id)` 로 시그니처 확장.

### 4.5 스케줄 레인
- 레이트리밋은 브로커·앱키 단위 → **NH 레인은 KIS 레인과 시간이 겹쳐도 무방.**
- NH 계좌 2개가 같은 앱키를 쓰면 NH1/NH2끼리 분·초 분리 (KIS 방식 재사용: worker 오프셋 + sync 분·초 레인).
- `schedule_map.py`에 NH1/NH2 레인 상수 추가.

### 4.6 대시보드·집계 (계좌 차원)
- `holdings_cache`: 계좌별 파일(`_holdings_<acct>.json`) 또는 단일 파일에 acct 필드
- `suite_metrics`: account 배열 반환 — 상단 KPI는 **전 계좌 합산** + 계좌 선택 필터(전체/KIS/NH1/NH2)
- `equity_snapshot`: 계좌별 시계열 + 합산 시계열 (자산추이 차트에 계좌 토글)
- 성과분석/매매일지: 전략 인스턴스(전략×계좌) 단위 블록
- 시스템설정: 계좌 관리 카드(등록·자격입력·연결테스트) + Kill Switch를 인스턴스 단위로

### 4.7 운영/배포
- Kill Switch: `STATE/<strategy>_<acct>.killed` (인스턴스 단위 영속)
- apply_deploy.sh: 인스턴스 DB·계좌 레지스트리 보존 목록 확장
- t_audit(정합감사)·취소오판 가드·전량청산 예외 등 기존 안전장치를 인스턴스 순회로 일반화

## 6. 리스크

1. **PLUG 출시 직후 안정성** — 2026-08-10 출시라 초기 버그·스펙 변경 가능. 모의서버 검증 기간을 넉넉히.
2. **LOC/MOC 미지원 리스크(§3.1)** — 최대 리스크. P0에서 최우선 확인.
3. WebSocket 부재 시 REST sync 의존 (KIS도 REST가 안전망이라 수용 가능).
4. 환전/증거금 정책 차이(KIS와 다를 수 있음) — 예수금 관리 로직 확인.
5. 대시보드 계좌 차원 도입 시 기존 화면 회귀 — 단계별 검증 필수.
6. 세금/양도세 계산은 계좌별 분리라 시스템 외 처리(현행과 동일).

## 7. 사용자 결정 필요 (구현 전)

1. **NH 계좌 2개의 용도**: 어떤 전략을 어느 계좌에? (예: NH1=VR(TQQQ — 계좌분리로 충돌 해소), NH2=종사종팔 2호/신규 전략 등)

4. 전략 인스턴스화 방식 A(주입형) vs B(복제형) — P1 착수 시 확정
